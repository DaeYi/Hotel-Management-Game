4. Incidents span all four flavors identified this session — guest-vs-guest conflict, operational near-misses/failures, reputation snowballs, and guest personality moments — from the first pass, not narrowed to one category — **agreed**.
5. Ship with a small starter catalog (not an exhaustive one) to prove the pacing system produces good moments before expanding it — **agreed**.

## Landscape Findings (this session)

Researched how other systems-driven games generate emergent stories:

- **RimWorld**: the AI Storyteller — a pacing/selection layer that decides *which* incident fires *when*, tuned to colony state — is the actual mechanism behind its narrative richness. Per-colonist depth is comparatively shallow; three storyteller "personalities" (Cassandra/Phoebe/Randy) demonstrate that pacing itself is the designed lever.
- **Dwarf Fortress**: the opposite bet — deep per-agent state (500+ interlocking needs/memories per dwarf) — stories emerge from agent-to-agent cascades.
- **Prison Architect**: explicitly modeled on Dwarf Fortress's philosophy (systems, not individuals).

**EUREKA (logged):** the original design doc's "Future Vision" language ("guests with inner lives that leak into the simulation") points toward the Dwarf Fortress model, which needs per-agent depth this project doesn't have and shouldn't try to build in one milestone. RimWorld's actual lesson — a well-designed selection/pacing layer on top of a comparatively shallow simulation — is the better-scoped bet here, since the guest-trait system it would sit on top of already exists.

Sources: [The Story Generator: A Game Design Analysis of RimWorld](https://zaydqazi.substack.com/p/the-story-generator-a-game-design), [AI Storytellers - RimWorld Wiki](https://rimworldwiki.com/wiki/AI_Storytellers), [Characterization and Emergent Narrative in Dwarf Fortress](https://www.researchgate.net/publication/356686095_Characterization_and_Emergent_Narrative_in_Dwarf_Fortress)

## Satisfaction System Design

Four interlocking pieces, all using `Guest.satisfaction` (0-100):

1. **Moves during the stay** — incidents push it up or down (a noise conflict drags it down; a resolved complaint or a personality-moment payoff lifts it), **plus a small ambient drift from overall stay quality** (gap found in eng-review D3: blends some of the same signals `calculateGuestReview` already tracks — condition, cleanliness, noise — into a slow per-tick nudge). Without this, most guests on a 1-3 night stay would never experience an incident (the pacing budget is deliberately small), so satisfaction would sit at its hardcoded initial value forever and return-guest/word-of-mouth would be nearly inert for ordinary play. Distinct from `reviewScore`, which is computed once at checkout from price fairness/condition/cleanliness/noise.
2. **Low satisfaction = incident fuel** — a guest below a satisfaction threshold becomes eligible for escalation-type incidents (conflict, walkout risk). This is the "powder keg" the pacing layer checks each tick.
3. **High satisfaction at checkout = return-guest eligibility** — satisfied guests can come back on a later visit as a recognizable returning guest, not a random new arrival. This is the visible loyalty payoff, and can itself trigger a personality-moment incident ("a regular is back"). **Concretely (gap found in review — `Guest` has no name field today and every guest is fully discarded on checkout, so "recognizable" needs real plumbing, not just a label):**
   - Add a `Guest.name` field, generated from a small hardcoded first-name pool for every guest (not just returners) — this also makes the story log read like "Sam complained about noise" instead of "a guest complained about noise," which the log needs anyway. **Known, accepted limitation (flagged in third review):** with a small name pool, two simultaneously-checked-in guests can share a name, making a log entry momentarily ambiguous. Not worth solving for this pass — accepted as-is; a room-number disambiguator is easy future work if it turns out to bother in play.
   - Add a small, capped `returningGuestPool` on `HotelState` (same retention pattern as `bookings`/`reviewWindowBookingCount` — cap the size, drop oldest first): a guest above the satisfaction threshold at checkout is added to it instead of fully discarded.
   - Guest-arrival generation gets a chance to pull a profile (name, trait, remembered room-type) from that pool instead of generating a fully fresh guest — that's what makes the return "recognizable": same name, same trait, logged as a return. **Scope note (gap found in second review):** for this pass, the remembered room-type is cosmetic/log-flavor only ("Sam is back, hoping for another suite") — it does not change `matchGuestToRoom`'s matching logic. Making it actually influence room assignment is future work, consistent with Premise 5.
4. **Rolling satisfaction feeds a word-of-mouth signal** — a secondary, slower-moving multiplier on arrivals, layered on top of `reviewScore`'s existing effect, so satisfaction has systemic weight even for guests who never return. **Window (gap found in review — this was undefined):** mirror `reviewScore`'s existing pattern — a rolling average of recent checkouts' satisfaction, using the same `REVIEW.reviewWindowBookingCount`-style shared constant rather than an independently-tuned window (exactly the kind of two-independently-tuned-numbers drift PR1 fixed elsewhere in this codebase). The exact multiplier curve is still open — see Open Questions.

## Incident Taxonomy (starter catalog, illustrative — not exhaustive)

Spans all four flavors the founder selected. Each is groundable in state the simulation already tracks (noise, condition, cleanliness, review deltas, guest traits including `party_guest`, amenity tiers):

- **Guest-vs-guest conflict**: Noise Complaint (a `light_sleeper` adjacent to high noise files a complaint) — built as the one causal **chain** for this pass (see Recommended Approach): complaint → if unresolved, escalates to early checkout / refund demand. **How satisfaction participates (gap found in third review — the chain's own trigger/escalation conditions and the Satisfaction System Design's point-2 threshold weren't connected anywhere):** the *initial* complaint is gated by the point-2 satisfaction threshold (a `light_sleeper` must already be below it, from accumulated noise exposure, to become eligible for the pacing layer to select this incident at all) — the escalation step itself is purely the stated time-based rule (unresolved for `hoursRemaining`), not a second satisfaction check; filing the complaint itself further lowers satisfaction, which is what the "powder keg" language in point 2 refers to. **Chain state:** lives in a new `activeIncidents: ActiveIncident[]` array on `HotelState` (`{id, type, guestId, roomId, stage, hoursRemaining}`), checked and advanced each tick alongside the pacing layer. **Teardown rule:** if the guest checks out, or *this incident's own room* becomes vacant some other way, the active incident is dropped — an already-departed guest can't escalate further, no error, no orphaned state. This is scoped to the incident's own guest/room pairing: if a guest is reassigned to a different room by an unrelated mechanic, a Noise Complaint chain tied to their old room is not silently killed by that reassignment — it either transfers to the new room or is explicitly resolved, not left ambiguous. **Cooldown:** once a guest has an active or recently-resolved Noise Complaint, they're excluded from becoming eligible for a new one for the rest of their stay — one complaint arc per guest per stay, not a chain that can re-trigger. **Culprit identification (gap found in eng-review D9):** `NoiseManager.calculateRoomNoise` currently sums up to 8 neighboring rooms' contributions into one scalar and discards the breakdown — with no identified offender, this isn't actually a guest-vs-guest incident, just ambient noise with a guest-shaped label. Fix: expose the per-source contributions instead of only the sum, and the complaint names the guest in the loudest contributing room as the culprit; `ActiveIncident` gains a second guest reference (`culpritGuestId`) alongside the complaining `guestId`. If no single source is strictly loudest (flat/uniform noise), the eligibility check fails closed — no complaint fires that tick, rather than picking an arbitrary culprit. **Timing (gap found in eng-review D10):** guests stay 1-3 nights (24-72h) and the chain (complaint → grace period → escalation) must complete before normal checkout (`daysStayed >= stayLength`) preempts it. The grace-period length (`ActiveIncident.hoursRemaining`'s starting value, already flagged as an open tuning number below) must be pinned against this 24-72h window *before* writing `StoryGenerator.ts` — not tuned after the fact — or the chain will rarely complete for a typical guest, silently failing the "genuine two-step chain" success criterion.
- **Operational near-miss**: Mid-Stay Breakdown — `room_broken` already fires as an inert event today; this pass gives it real consequences: see "Early Departure & Refund Mechanic" below for exactly what "move or comp" means.
- **Reputation snowball**: Review Goes Semi-Viral — an unusually bad checkout review triggers a temporary arrival penalty, logged with a specific cause named. **Attribution rule (gap found in review, corrected in second review — the first version only compared 3 of the ~6 real negative contributors, risking a misleading cause; corrected again in third review — a leftover "four" from an earlier draft didn't match the five-item list, and the price-fairness condition was stated as one-directional when the underlying formula isn't):** `calculateGuestReview` (`GuestManager.ts`) already computes `noisePenalty`; the negative side of `conditionBonus` and `cleanlinessBonus`; `amenityPenalty` (already unidirectional — there's no positive side); and a `priceFairness`-driven shortfall when price diverges significantly from the room type's expected price **in either direction** (the formula `1 - |price - expectedPrice| / expectedPrice` penalizes underpricing and overpricing identically — an implementer checking only "too expensive" would miss half the real cases). The cause named is whichever of those **five** is numerically largest; `guestVariance` (pure randomness) is deliberately excluded from consideration — attributing a bad review to "random bad luck" isn't an actionable narrative cause, so it's never the named reason even when it's mathematically the biggest single contributor. Ties break in a fixed order: noise, then condition, then cleanliness, then amenities, then price. **Implementation note:** these components are currently local variables inside `calculateGuestReview`, not returned to callers — this attribution rule requires that function's return type to change (return a breakdown, not just the final score), which is real scope, not just "reading state already tracked."
- **Personality moment**: A Regular Returns — the visible face of the return-guest mechanic; a satisfied guest's comeback, logged as a small vignette.

## Early Departure & Refund Mechanic (gap found in second review — genuinely uncosted before this)

Two of the four starter incidents (Noise Complaint's escalation, Mid-Stay Breakdown) require a guest to leave *before* their booked `stayLength` — a mechanic that does not exist today. Verified against the actual code: `GuestManager.processDepartures` only ever processes a departure when `daysStayed >= guest.stayLength`, and `EconomyManager.processRevenue` computes payment as a single lump sum (`nightRate * stayLength`) at that full-length checkout. There is no partial-stay billing or early-departure path anywhere in the simulation. This is new scope, not a reuse of existing checkout logic, and needs its own small design:

- **Trigger:** an incident's escalation (unresolved Noise Complaint, or a Mid-Stay Breakdown with no vacant room to move the guest to) marks the guest for early departure on the next tick, bypassing the normal `daysStayed >= stayLength` check.
- **Pipeline integration (gap found in eng-review D1 + D7):** the early-departure check runs as its own step in `tick.ts`, immediately *before* the existing step-2 `processDepartures` call, with an explicit guard against double-processing a guest whose `daysStayed` also reaches `stayLength` in the same tick an incident escalates for them (whichever condition fires, the guest is removed once, not twice). It folds into the *same* `departedGuestIds`/`newBookings`/`roomsAfterDeparture` accumulation that step 2 already builds for normal checkouts, rather than running as a second, parallel mini-pipeline — verified against `tick.ts:38-73`, which currently builds all four (who left, new bookings, cleaning trigger, revenue total) from one `processDepartures` call. A parallel block risks a room silently never entering cleaning, or a guest counted twice.
- **Booking record (gap found in eng-review D2 + D4):** an early-departed guest still creates a `Booking`, using the real `calculateGuestReview` breakdown (now returned, not just the final score — see the Review Goes Semi-Viral attribution rule above) minus an additional incident penalty, not a flat fixed low value. This keeps walkouts inside the existing `reviewScore`/star-rating feedback loop instead of making them invisible to it.
- **Event type (gap found in eng-review D8):** a walkout emits a new event type (not `guest_departed`), so it doesn't blend into `GameScene.ts`'s existing Finance-chart revenue accumulator (`event.type === 'guest_departed'` reading `data.totalPaid` as gross full-stay revenue today) or `NotificationToast`'s existing departure batching. Both consumers need to be updated to also handle the new type as part of this change, or walkouts become invisible in UI that already ships.
- **Refund/comp (formula corrected in third review — the original "not clawed back" framing assumed an accrual/prepayment billing model this codebase doesn't have; `processRevenue` only ever collects one lump sum at full checkout, so there's nothing already "collected" mid-stay to protect):** this mechanic pays revenue for the nights actually stayed, then applies a comp on top, as new logic parallel to (not a modification of) `processRevenue`'s existing full-stay lump sum. Concretely: `revenue = nightRate * daysStayed`, `comp = ECONOMY.earlyDepartureRefundRate * nightRate * nightsRemaining`, `cashDelta = revenue - comp` (a fixed named constant, mirroring the existing `ECONOMY.demolishRefundRate` pattern — not an ad hoc number).
- **Room-move alternative (Mid-Stay Breakdown only):** if a vacant, condition-healthy room of the same type is available, the guest can be reassigned to it instead of departing — no refund in that case, just a room swap and a satisfaction bump for the resolution.
- **Vacated room:** re-enters normal turnover cleaning exactly like any other checkout — no special-cased room state.

This effectively adds a second, narrower departure pathway alongside `processDepartures`'s existing full-stay path. Scoped here explicitly so it's counted in the effort estimate below, not discovered mid-build.

Expanding the incident catalog beyond these four is explicit future work (Premise 5) — not part of this pass's Success Criteria.

## Approaches Considered

### Approach A: Minimal Viable — Threshold-Triggered Incidents
Simple deterministic rule checks each tick, woven into `tick.ts`. Story log as a capped array on `HotelState`.
- Effort: M (human: ~1-2 weekends / CC: ~2-3h) — Risk: Low-Med
- Pros: fastest, reuses existing patterns exactly
- Cons: no real pacing — undermines the RimWorld insight (pacing, not triggers, is what makes incidents feel authored)
- Reuses: `GameEvent` union, tick.ts pipeline, PRNG, existing guest traits

### Approach B: Ideal Architecture — Storyteller/Pacing Layer
A dedicated `StoryGenerator.ts`: scans for eligible incidents each tick, then *selects* among them using a pacing budget (caps incidents/day, weights toward "it's been quiet too long"). A real selection algorithm, not independent triggers.
- Effort: L (human: ~3-4 weekends / CC: ~5-6h) — Risk: Med
- Pros: captures the actual RimWorld mechanism
- Cons: most novel code, most of the tuning risk lives here
- Reuses: same as A, plus a new pacing/selection algorithm

### Approach C: Creative/Lateral — Causal Incident Chains
Multi-step incidents (Noise Complaint → unresolved for N hours → Guest Walks Out) with real cause→effect visible in the log — the exact differentiator the eng-review's landscape check flagged versus Hotel Magnate's persona variety.
- Effort: L-XL (human: ~4-5 weekends / CC: ~6-8h) — Risk: Med-High
- Pros: truest execution of the milestone's actual purpose
- Cons: needs new "active incident" state tracking, biggest scope risk for a first pass

## Recommended Approach

**Approach B, with Approach C applied to exactly one starter incident** (the Noise Complaint chain). The pacing layer is non-negotiable — without it, incidents degrade to "more toast messages" and the whole differentiation argument collapses. Going all-in on chains for every starter incident risks the scope blowout the original design doc explicitly warned about. One real chain proves the differentiator works before the catalog expands.

**Effort/Risk for the recommended combination (gap found in review, revised in second review after the early-departure mechanic surfaced as real, previously uncosted scope):** Effort: L, at the top of Approach B's L range — human: ~5-6 weekends / CC: ~8-10h. This now explicitly includes: the return-guest plumbing (name field, `returningGuestPool`, arrival-generation hook), the `activeIncidents` chain-state array, the `calculateGuestReview` return-shape refactor needed for review attribution, and the early-departure/refund pathway (new scope, not a reuse of existing checkout logic — see "Early Departure & Refund Mechanic"). Risk: Med-High — the early-departure mechanic is a second, genuinely novel subsystem alongside the pacing layer itself, not just plumbing around it. **Eng-review addendum:** the culprit-identification change (D9), new event type wiring (D8), and balance-harness rebaseline (D11, see Open Questions) add modest, contained scope on top of this estimate — not enough to move the L rating, but worth listing explicitly rather than discovering them mid-build.

6. `returningGuestPool` sizing (how many past guests to retain, how long they stay eligible before aging out) — needs a starting number but isn't worth debating on paper; pick something small (e.g. 10-20) and adjust from play.
7. Probability of pulling a returning guest from the pool vs. generating a fresh arrival — needs a starting number (e.g. a flat 10-15% chance per arrival slot when the pool is non-empty), same "pick something small and tune from play" caveat as #6.
8. `storyLog` retention size (see Story Log Entry Schema below — capped like `returningGuestPool`, but the exact cap is a tuning number, not a design decision).
9. Four more tuning numbers surfaced in the third review, same "pick something small, tune from play" treatment as #6-#8: the incident-fuel and return-guest satisfaction thresholds (Satisfaction System Design points 2 & 3), the unresolved-hours window before a Noise Complaint escalates (`ActiveIncident.hoursRemaining`'s starting value — **note:** per D10 above, this one specifically must be pinned against the 1-3 night stay distribution *before* implementation, not tuned after like the others here), `ECONOMY.earlyDepartureRefundRate`'s value, and what condition threshold counts as "healthy" for the Mid-Stay Breakdown room-move alternative.
10. **Arrival death-spiral risk (gap found in eng-review D11):** `reviewScore`'s existing arrival-scaling already divides by a rolling-window factor (`GuestManager.ts`); D2/D4 now put real, incident-penalized, low-score walkout `Booking`s into that same window, which is small early-game, so a handful of walkouts can swing it hard. The new word-of-mouth multiplier (Satisfaction System Design, point 4) stacks a *second*, independently-tuned arrival penalty on the same root cause. Before calling this milestone done: cap/dampen the word-of-mouth multiplier's floor, and add a walkout-heavy scenario to `simulate.ts`'s balance harness to confirm the two mechanics don't compound into an early-game arrival spiral neither was individually tuned to produce.

## Story Log Panel — Visual & Interaction Spec (gap found in design review)

**Design tokens (D5, design review — no DESIGN.md exists yet; these are the de facto tokens verified in `FacilityInspector.ts`, proven across 3 existing panels):** background fill `#1a1a3e` at 95% opacity, border `#6a6a8a` (1px), font `monospace` throughout — no sans-serif. Text hierarchy: `#ffffff` for the entry message (primary), `#888899` for timestamps/secondary labels, `#aaaacc` for supporting body text, `#e74c3c` reserved for negative/cost content (matches its existing use for demolish/repair costs elsewhere — do not reuse it for incident severity, which needs its own treatment). Close button matches the existing `RoomInspector`/`FacilityInspector` chrome.

**Layout hierarchy (D1, design review):**

```
+--------------------------------------+
| STORY LOG                        [X] |  <- title (14px white) + close, matches existing panel header row
+--------------------------------------+
| Day 12, 3pm                           |  <- timestamp: small, muted (#888899, 12px)
| Sam filed a noise complaint           |  <- message: primary (14px #ffffff)
| about Room 4.                         |
|   |                                    <- chain connector: indented + vertical
|   Day 12, 7pm                            line links this entry to the one above
|   Complaint escalated -- Sam checked     as one thread, not two unrelated lines
|   out early.
|                                        <- unrelated entry: NOT indented, no connector
| Day 11, 9am                           |
| A Regular Returns: Priya is back!     |
+--------------------------------------+
```

Newest-first, with an explicit ordering + eviction rule (gap found by outside voice, D11): a chain's list position tracks its most recent event — an escalation bumps its whole thread to the top of the list; within a thread, entries stay chronological (origin first, escalation below it, indented). Cap-eviction (Open Questions #8) operates on whole chains, not individual entries — a chain is retained or evicted as one unit, so an escalation is never shown without the complaint that caused it (the "orphaned escalation" failure mode an outside-voice review flagged).

Chain-linked entries (shared `chainId`) render indented under their originating entry with a vertical connector; standalone entries render flush-left with normal spacing. This is the one visual mechanism doing the "legible cause-and-effect" work the Problem Statement promises — it's not optional polish.

**Room references (gap found by outside voice, D9):** verified against the actual code — `Room.id` is `room-${gridX}-${gridY}` (internal only) and `RoomInspector`'s title is just `"${typeName} Room"`; no player-facing room number exists anywhere in this codebase today, so "Room 4" in a log message would reference something the player cannot look up. Fix: a pure formatting function, `formatRoomLabel(gridX, gridY)`, deriving a hotel-style number from grid position (floor = row, unit = column, e.g. `"Room 204"` for row 2, column 4) — no new stored data. Used in three places: `RoomInspector`'s title (currently just `"Suite Room"`), a new small label rendered on each grid tile (`GridRenderer`), and `StoryGenerator`'s log/toast message text. This closes a gap that already existed before this milestone (`room_broken` toasts today reference no room number either) as a side effect of fixing it for the story log.

Whole-game accessibility gaps (no keyboard navigation anywhere — verified, no `keydown` handlers exist in this codebase; no ARIA/screen-reader support — structurally unavailable on a Phaser canvas without a parallel DOM layer) are pre-existing architecture decisions made before this milestone, not introduced by it, and are explicitly out of scope here (see "NOT in Scope").

## Incident Visibility — Toast + Panel (gap found in design review, D4)

The Story Log panel is toggle-able and hidden by default (D6, eng-review) — without a complementary signal, a player who doesn't have it open never learns an incident happened. Rather than building the always-on HUD deferred to TODOS.md, notable incident moments (a Noise Complaint filed, an escalation, "A Regular Returns") also fire a brief toast via the existing `NotificationToast.ts` system — the same file already being extended for the new walkout event type (D8, eng-review). This means `EVENT_COLORS` gains a few new entries for incident event types, and `StoryGenerator.ts`'s event emission calls into the same toast pipeline `tick.ts` already uses for `room_broken`, `guest_departed`, etc. Not every `StoryLogEntry` needs a toast — routine/low-signal entries can log silently; the toast is reserved for moments worth a glance. **Panel-open suppression (gap found by outside voice, D13):** verified against `GameScene.ts` — toasts render at depth 25-26 near the grid's bottom-left; panels render at depth 18-20 with an x-range that overlaps the toast's, so an incident toast can visually collide with the Story Log panel itself if the player already has it open. Since the player is already looking at the panel in that case, the toast is both redundant and a visual collision risk — incident-specific toasts are suppressed while the Story Log panel is open (other toast types, e.g. `room_broken`, are unaffected).

## Return-Guest Visual Marker (gap found in design review, D7)

The Success Criteria require return guests to be "shown with the same name and trait as their prior stay, not just a generic 'returning guest' flag" — this needed a concrete visual mechanism, not just log text. Fix: a small ring/outline drawn around the returning guest's existing trait-color dot in `GridRenderer.ts` (extends `getGuestDotColor`'s existing per-guest draw call, no new art assets), plus story log phrasing that reads distinctly from a fresh arrival ("Sam is back for another stay!" vs. "Sam checked in"). This makes the return-guest payoff visible on the grid during actual play, not only discoverable after the fact in the log.

**Data to key the marker off (gap found by outside voice, D10):** verified against `types.ts` — `Guest` (lines 35-42) has no field distinguishing a returning guest from a fresh one, and `returningGuestPool` entries are consumed once pulled, so nothing in state survives to let `GridRenderer` branch on this. Fix: add `Guest.isReturning: boolean`, set `true` when arrival generation pulls a profile from `returningGuestPool` instead of generating fresh. This rides the same v9→v10 migration already touching `Guest` for the name backfill (D5, eng-review) — in-progress guests loaded from a pre-v10 save backfill `isReturning: false` alongside their generated name.

## Save Compatibility

This milestone adds new state: `Guest.name`, `Guest.isReturning` (design review D10), `HotelState.activeIncidents`, `HotelState.returningGuestPool`, and `HotelState.storyLog`. Old saves (currently `SAVE_VERSION = 9`) won't have any of these fields. Per the existing `SaveManager.ts` convention (a new version block per schema change, default-filling missing fields), this needs a `v9 -> v10` migration step — not a "saves may break" footnote. Add it as part of this milestone's implementation, not a follow-up. **Scope clarified in eng-review (D5):** the migration must also map over `state.guests` (not just default-fill the new top-level `HotelState` fields) to backfill a generated `name` onto guests already checked in inside a loaded save — mirroring the existing `v2 -> v3` migration's pattern of mapping over `state.rooms` to backfill new per-room fields. Verified against `SaveManager.ts`: every prior migration step that touches per-entity state maps over the array; a migration that only default-fills new `HotelState` keys would silently leave in-progress guests nameless.

  |

  |     -> departedGuestIds, newBookings (incl. walkout Bookings, D2/D4), roomsAfterDeparture, revenue

## Failure Modes (per new codepath)

| Codepath | Failure mode | Detection/mitigation |
|---|---|---|
| Early-departure step (D1/D7) | Guest double-processed (removed by both the early-departure step and step 2's normal check in the same tick) | Dedicated regression test (per Test Plan); explicit guard checked before step 2 runs |
| Early-departure step (D7) | Vacated room never enters cleaning (parallel-pipeline risk avoided by folding into step 2's accumulation) | Same accumulation path as normal checkout exercises this already; no separate code to fall out of sync |
| Walkout Booking (D2/D4) | `calculateGuestReview` refactor changes existing scores, breaking the byte-identical regression requirement | Regression test pinning existing test cases' exact output, before/after the breakdown-return refactor |
| Walkout event (D8) | Finance chart or NotificationToast silently drop or mis-account walkouts if the new event type isn't wired into both | Manual QA per Test Plan's Key Interactions; both consumers explicitly updated as part of this change, not deferred |
| Noise Complaint culprit (D9) | No neighbor is actually louder than a base threshold (flat/uniform noise) — ambiguous or arbitrary culprit selection | Fails closed: no complaint fires that tick rather than picking an arbitrary culprit |
| Noise Complaint chain (teardown rule, third review) | Chain silently killed by an unrelated room reassignment | Teardown already scoped to the incident's own guest/room pairing (Incident Taxonomy); covered by the Test Plan's edge case |
| Noise Complaint timing (D10) | Grace period longer than typical remaining stay — chain almost never escalates | Timing pinned against the 1-3 night stay distribution before implementation, not tuned after |
| Word-of-mouth + walkout scoring (D11) | Compounding arrival penalty (rolling reviewScore window + new word-of-mouth multiplier both driven by the same walkouts) — early-game arrival death-spiral | Word-of-mouth floor cap; `simulate.ts` balance harness gets a walkout-heavy scenario before calling this done |
| Save migration (D5) | In-progress guests loaded from a pre-v10 save have no `name`, story log reads "undefined complained about noise" | Migration maps over `state.guests`, not just new `HotelState` fields, backfilling a generated name |
| `returningGuestPool` | Pool empty (early game, no satisfied checkouts yet) | Arrival generation falls through to fresh-guest generation cleanly (Test Plan edge case) |
| Word-of-mouth window | Fewer bookings than window size (cold start) | Matches `updateReviewScore`'s existing cold-start handling (Test Plan edge case) |
| Story log chain eviction (design-review D11) | Cap-eviction drops a chain's origin entry but keeps its escalation, reading as a non-sequitur | Cap-eviction operates on whole chains as a unit (grouped by `chainId`), never orphaning an escalation |
| Story log room references (design-review D9) | Log message names a room the player has no way to locate (no player-facing room number exists pre-this-milestone) | `formatRoomLabel(gridX, gridY)` gives every room a stable, displayed number, used consistently in the log, `RoomInspector`, and the grid tile itself |
| Incident toast (design-review D13) | Toast visually collides with the Story Log panel if the player already has it open (confirmed depth/x-range overlap in `GameScene.ts`) | Incident-specific toasts suppressed while the panel is open |
